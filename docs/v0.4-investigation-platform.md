# nScout v0.4.0 — Investigation Platform

v0.4 turns the v0.3 security-intelligence foundation into a persistent analyst workflow. Full AI Analyst remains deferred to v0.5; threat-intelligence providers and Sensor Mode remain later milestones.

## Cross-platform desktop priority

v0.4 now targets normal desktop installation on **Windows, Linux and macOS**. The existing React/FastAPI application remains the product core and Tauri remains the preferred shell; platform support must not become three divergent application implementations. Packaging success alone does not qualify a platform as supported. Each platform must pass clean-install launch, silent backend readiness, shutdown/orphan cleanup, interface enumeration, live capture permissions, PCAP workflows, investigation persistence and report/export validation before release support is claimed.

Capture implementations may differ by operating system behind the shared provider capability interface. The Windows Pktmon/WFP work is Windows-specific and must not be forced onto Linux or macOS. Existing capture functionality remains the compatibility baseline, and dependency removal must not regress packet fidelity or investigation features.

## Engineering rules
- Develop on `v0.4-investigation-platform`, not directly on `main`.
- Keep changes reviewable and regression-tested.
- Do not expose inactive AI controls when AI integration is disabled.
- Treat a host as Active/Recently Seen/Inactive based on observation timestamps; passive capture cannot prove that a silent host is offline.
- Never describe TLS metadata inspection as encrypted payload decryption.
- Preserve v0.3 behavior unless a v0.4 change intentionally replaces it.

## Investigation Workspace API (v0.4 development)

Investigation cases persist as atomic JSON records under
`~/.nscout/investigations` by default, or under
`$NSCOUT_DATA_DIR/investigations` when the data directory is overridden. This
storage is independent of MongoDB so notes and evidence remain available in a
local-only installation.

The development API supports creating, listing, loading, renaming and deleting
investigations; adding/removing deduplicated packet, host, connection, DNS,
finding and timeline evidence; adding analyst notes; and moving findings through
the documented lifecycle. Evidence snapshots are size-bounded, IDs are validated
before file access, and malformed records are skipped in case listings rather
than breaking the whole workspace.

The **Investigations** tab can create, select and delete local cases; remember
the active case; bookmark the selected packet plus observed hosts and security
findings; remove evidence; add analyst notes; reopen packet evidence; and move
bookmarked findings through the lifecycle. Additional one-click bookmark actions
on DNS, TLS, connection and timeline rows remain under development.

## Local LLM integration (v0.4)

Optional packet, finding and connection explanations can use a model server on
the same computer as nScout. Full AI Analyst remains a v0.5 milestone.

1. Start Ollama with a locally downloaded model, or load a model and start the
   server in LM Studio's Developer tab.
2. Open **Settings → AI integration**, enable AI and select the provider.
3. Use `http://127.0.0.1:11434/v1` for Ollama or
   `http://127.0.0.1:1234/v1` for LM Studio. Custom local OpenAI-compatible
   servers are also supported.
4. **Test connection / discover models**, choose or enter the exact model ID,
   adjust timeout/output limits if needed and **Save**.

Testing retrieves `/models` without sending capture evidence; inference uses
`/chat/completions`. Local answers arrive through the existing SSE format after
completion, rather than token by token. The first request may take longer while
the model loads. AI actions are hidden when AI is disabled, and the backend also
enforces the OFF default.

Local providers need no cloud key. For authenticated local servers, set
`NSCOUT_LOCAL_AI_KEY` in the backend environment. Keys are never returned through
settings or stored in the frontend. The existing cloud provider remains an
explicit selection using `EMERGENT_LLM_KEY`. Local failures never trigger cloud
fallback. Select an actually local model in the model server: a loopback server
can itself be configured to proxy to cloud models.

Settings persist atomically in `~/.nscout/ai-settings.json` without MongoDB;
override the directory with `NSCOUT_DATA_DIR`. Local URLs must use loopback.
HTTP redirects and proxy environment variables are ignored. Selected context,
responses and output tokens are bounded. One local explanation runs at a time.
Failures show an actionable message and observed deterministic context. Capture,
protocol analysis and investigations remain available without AI.

## Capture switching and retention (v0.4 development)

Changing the selected interface while capture is running now performs a
serialized stop/switch/start transition. The local preference controls whether
the current packets and derived investigation state are preserved or cleared.
The configured packet limit is applied when capture starts, when an interface
switches and immediately when Settings is saved. Oldest packets are evicted
first, their packet-detail index entries are removed at the same time, and the
status API reports both the active limit and cumulative retention evictions.

Each runtime capture now has a local identifier and records bounded interface
transition metadata without packet content. `GET /api/capture/diagnostics`
reports requested versus actual mode, health, last-packet time, buffer pressure,
retention evictions and interface history. The UI makes degraded live-capture
fallback explicit instead of silently presenting simulated traffic as live, and
saved capture snapshots retain their source interface/session provenance.

## Local Capture Sessions (v0.4 development)

New capture snapshots persist as atomic JSON records under
`~/.nscout/capture-sessions`, or `$NSCOUT_DATA_DIR/capture-sessions` when the
data directory is overridden. Saving, listing, replaying and deleting snapshots
does not require MongoDB. Existing MongoDB-backed snapshots remain visible and
loadable when MongoDB is configured, providing a gradual migration path.

Each snapshot records capture identity, interface/mode provenance, retention
and interface-transition metadata, packets needed for replay, and observed
threats. A local snapshot keeps at most the newest 100,000 buffered packets and
marks itself as truncated when its source capture was larger. Snapshot IDs are
validated before file access, writes are atomic, oversized/unreadable records
are isolated, and list results are capped at the newest 100 sessions.

## Keyboard shortcuts (v0.4 development)

Settings now contains a searchable Keyboard Shortcuts section generated from
the same registry used by the application's global key handler. The header
question-mark button and the `?` key open this section directly. Implemented
shortcuts include packet-filter focus, Settings, Capture Sessions, capture
start/stop, Global Investigation Search (`Ctrl`/`Command` + `Shift` + `K`),
drawer dismissal and direct navigation to each primary workspace.
Shortcuts that would conflict with typing or activating a control are ignored
while an interactive field has focus.

## Global Investigation Search (v0.4 development)

The header **Search** action opens a debounced, local search surface covering
live packet summaries, host identities, reconstructed connections, DNS events,
security findings and correlated timeline events, plus persisted investigation
names/descriptions, analyst notes and evidence labels/references. Results are
ranked and grouped by type and can reopen packet detail, host-filtered traffic,
flow context, intelligence panels or the owning saved investigation.

The API requires at least two characters, caps source scans and results, and
does not index raw packet layers, payload, ASCII/hex views or persisted evidence
snapshot bodies. This boundary keeps broad search useful without turning packet
contents into an implicit secondary data store. The development endpoint is
`GET /api/search?q=<query>&limit=<1-100>`.

## Investigation Report 2.0 (v0.4 development)

The live Intelligence workspace and each saved Investigation case expose PDF,
HTML, JSON, CSV, XLSX and XML downloads. All formats derive from one report
schema containing protocol/connection intelligence, host context, defensive
findings and the correlated timeline. Case exports also include case metadata,
Evidence Locker references, analyst notes and finding lifecycle states.

When **Settings → Investigation & privacy → Redact exported reports** is enabled,
the export request applies stable report-local aliases to IP addresses, MAC
addresses and domains in structured fields and free text. Aliases stay consistent
inside one report so relationships remain understandable without exposing the
original identifiers. Raw packet payloads, ASCII/hex views, packet layers and
Evidence Locker snapshot bodies are never embedded. CSV/XLSX text beginning
with spreadsheet formula characters is neutralized before export.

The development API is
`GET /api/investigation/report.<format>?workspace_id=<optional-id>&redact=<bool>`,
where `<format>` is `pdf`, `html`, `json`, `csv`, `xlsx` or `xml`.

## PCAP Comparison (v0.4 development)

The PCAP Investigation workspace can compare a baseline capture with a current
capture without clearing, stopping or replacing the active nScout session. Each
file is parsed into its own isolated analysis context. The comparison reports
packet, byte, duration, host, domain, connection and finding-count deltas;
protocol, service-port, finding-severity and TCP-health changes; plus added and
removed hosts, domains and flows. Differences are investigation observations,
not automatic claims of compromise.

Each file is limited to 50 MB and analysis is capped at 100,000 packets. The
response records the original filename, byte size, SHA-256 digest, capture time
range, analyzed packet count and whether the bound truncated the input. The UI
surfaces truncation explicitly and can save the result as JSON. Raw payload,
ASCII and hex content are not returned by the comparison endpoint.

The development API is `POST /api/pcap/compare` with multipart fields
`baseline` and `current`.

## Live Hosts (v0.4 development)

The dedicated **Live Hosts** workspace combines current passive-capture host
evidence with local analyst metadata. It supports search across IP address,
alias, hostname, MAC address, protocol and correlated domain; activity-state
and watchlist filters; persistent analyst aliases; and host-focused views of
peers, domains, findings and bounded observation history. Selecting **Packets**
opens the packet workspace with that host applied as its filter.

Aliases, watchlist state, last-known passive identity and up to 100 sightings
per host persist atomically in `$NSCOUT_DATA_DIR/host-profiles.json` (or the
default `~/.nscout` data directory) without MongoDB. Sightings contain
timestamps and packet/byte totals, not packet payloads. **Active now** means
traffic was observed within 60 seconds, **Recently seen** within 15 minutes,
and **Inactive** means no traffic was observed inside those windows. These
labels intentionally do not claim that a silent host is offline.

## Packet timestamps (v0.4 development)

Packet evidence retains its Unix epoch plus an explicit UTC ISO-8601 transport
timestamp. The packet table and inspector derive their display time from the
epoch in the operating system/browser timezone, fixing the earlier UTC clock
being shown as if it were local time. Live capture uses the packet arrival time;
PCAP imports preserve each packet's original capture epoch. No timezone is
hard-coded, so the behavior follows the host on Windows, Linux and macOS.

Prompts adapt to selected evidence and treat capture content as untrusted data.
Explanations distinguish observation from uncertainty and never claim to decrypt
encrypted application payload. AI output remains advice for analyst review.
