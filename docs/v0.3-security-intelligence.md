# nScout v0.3 Security Intelligence

This guide documents the Security Intelligence capabilities introduced on the
`v0.3-security-intelligence` branch. The release builds on the v0.2 packet and
connection investigation workflow; it does not replace raw packet evidence or
claim that a heuristic finding proves compromise.

## Capability overview

| Capability | What it adds |
|---|---|
| Detection Engine 2.0 | Explainable passive heuristics with severity, confidence, state and structured evidence. |
| Host Intelligence | Host-centric identity, traffic, services, domains, peers, findings and risk scoring. |
| Investigation Timeline | Ordered correlation of DNS, TCP, TLS, HTTP and security events. |
| Advanced Packet Search | Boolean expressions, comparisons, parentheses and protocol-aware fields. |
| Security Operations Dashboard | Security posture, severity distribution, risky hosts and recent findings. |

## Detection Engine 2.0

The engine analyzes observable packet metadata and produces investigation leads.
Every finding contains a type, title, severity, confidence, investigation state,
timestamp, related endpoints, optional packet ID and structured evidence.

Current passive heuristics include:

- ARP identity changes for an IP observed with multiple sender MAC addresses.
- Failed TCP connections and excessive failed-connection activity.
- Fast TCP port scans across many destination ports.
- Regular outbound connection timing that may warrant beaconing review.
- Unusually long DNS queries and high DNS query fan-out.
- Packet-rate spikes relative to the capture's non-empty baseline.
- Large directional transfers between two IP addresses.
- Traffic to clearly special or reserved destination ranges.

Thresholds are intentionally conservative and operate only on the available
capture window. NAT, asymmetric capture, packet loss and short captures can all
change the evidence available to a rule.

### Finding model

```json
{
  "type": "network.port_scan",
  "severity": "high",
  "confidence": "high",
  "state": "new",
  "title": "Possible TCP port scan",
  "detail": "Source probed multiple TCP ports in a short window.",
  "packet_id": "packet-id",
  "src_ip": "10.0.0.15",
  "dst_ip": "10.0.0.20",
  "evidence": [
    {"target": "10.0.0.20", "ports": [22, 80, 443], "window_seconds": 8.4}
  ]
}
```

## Host Intelligence

Host profiles are built from passive evidence. Profiles include:

- IP address, observed MAC address and correlated hostname when available.
- Local/external classification.
- First/last observation time.
- Sent, received and total packet/byte counts.
- Protocols and observed service ports.
- DNS, HTTP Host and TLS SNI domain observations.
- Peer connections with ports, protocols, bytes and observation times.
- Findings involving the host.
- A bounded risk score from 0 to 100.

### Risk scoring

Risk is a prioritization aid rather than a probability of compromise. Each
finding contributes severity points adjusted by confidence:

| Severity | Base points |
|---|---:|
| Critical | 40 |
| High | 25 |
| Medium | 12 |
| Low | 4 |

Confidence multipliers are `high = 1.0`, `medium = 0.8` and `low = 0.5`.
Scores are capped at 100 and mapped to the following levels:

- `0`: none
- `1–24`: low
- `25–49`: medium
- `50–74`: high
- `75–100`: critical

## Investigation Timeline

The correlated timeline orders evidence from multiple protocol views into one
sequence:

`DNS query/answer -> TCP connection -> TLS or HTTP activity -> security finding`

DNS answers are used to attach relevant domain context to later connections.
Analysts can filter by host, domain, connection/port, protocol, minimum severity
and time range, then open the related packet when a packet ID is available.

## Advanced Packet Search

The parser is implemented without `eval` or dynamic code execution. It supports:

- `AND`, `OR` and `NOT` (case-insensitive).
- Parentheses and standard precedence: `NOT`, then `AND`, then `OR`.
- `=`, `==`, `!=`, `>`, `>=`, `<`, `<=` and `contains`.
- Quoted values through shell-style tokenization.
- Implicit `AND` and the original compact filters for backward compatibility.

### Search examples

```text
protocol == DNS
(port == 443 OR port == 8443) AND NOT tcp.reset
domain contains example.com
http.method == POST AND http.status >= 400
tls.sni contains example.org
severity >= high
ip:10.0.0.15 port:443 bytes>1000
```

### Searchable fields

| Category | Fields |
|---|---|
| Packet | `protocol`, `bytes`, `length`, `info`, `flags` |
| Address | `ip`, `src`, `src_ip`, `dst`, `dst_ip` |
| Port | `port`, `srcport`, `src_port`, `dstport`, `dst_port` |
| DNS | `domain`, `dns.query`, `dns.rcode` |
| HTTP | `http.host`, `http.method`, `http.status` |
| TLS | `tls.sni` |
| TCP health | `tcp.reset`, `tcp.retransmission`, `tcp.out_of_order`, `tcp.duplicate_ack`, `tcp.zero_window` |
| Security | `severity` |

Malformed expressions return HTTP 400 with a validation message. Search results
are limited server-side, with an upper bound of 5,000 packets per request.

## Security Operations Dashboard

The Analytics tab combines traffic and defensive context:

- Current capture state and overall security posture.
- Packet, throughput, host and finding KPIs.
- Traffic-over-time and protocol-distribution charts.
- Severity distribution and high-priority finding counts.
- Hosts ranked by risk score with investigation drill-down.
- Recent findings and direct navigation to the Security workspace.
- Top talkers ranked by observed traffic.

Host profiles refresh only while the Analytics tab is active, avoiding continuous
recomputation when the dashboard is not being viewed.

## API reference

All paths below are relative to `/api`.

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/intelligence/hosts` | Return host profiles and risk data. |
| `GET` | `/intelligence/timeline` | Return correlated investigation events. |
| `GET` | `/packets/search?expression=...&limit=...` | Validate and execute an advanced packet filter. |
| `GET` | `/investigation/summary` | Return the integrated investigation data model. |
| `GET` | `/investigation/report.json` | Download the investigation as JSON. |
| `GET` | `/investigation/report.html` | Download a standalone HTML report. |
| `GET` | `/investigation/report.pdf` | Download a PDF report. |

Timeline query parameters are `host`, `domain`, `connection`, `protocol`,
`min_severity`, `start`, `end` and `limit`. Times are Unix timestamps.

## Analyst workflow

1. Start a live/simulated capture or import an authorized PCAP.
2. Open **Analytics** to assess posture, severity and highest-risk hosts.
3. Open a risky host or the **Intelligence** workspace to inspect peers, domains
   and associated findings.
4. Use **Timeline** to reconstruct the order of related events.
5. Use **Advanced Packet Search** to isolate supporting packets.
6. Open packet details to inspect protocol layers and raw evidence.
7. Export JSON, HTML or PDF when the investigation needs to be shared.

## Validation

The v0.3 branch currently has 52 focused backend regression tests covering the
deterministic analysis modules, including Detection Engine 2.0, Host Intelligence,
the Investigation Timeline and Advanced Filtering. Python compilation, JSX bundle
validation and whitespace checks are also run during development.

The repository's full integration tests expect a running application environment
and are distinct from the focused module suite. Windows packaging and CI remain the
final release-candidate gate.

## Security and privacy notes

- Analyze only networks and packet captures you are authorized to inspect.
- HTTPS application payload remains encrypted; nScout uses observable metadata.
- Findings are leads for analyst review, not automatic attribution or proof.
- Avoid sharing exported reports until sensitive addresses, domains and payload
  excerpts have been reviewed.
- Do not expose the desktop API to an untrusted network without adding appropriate
  authentication and access controls.
